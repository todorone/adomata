# Insights are stored at Ad grain only; every other tree level is a computed rollup

CONTEXT.md's fixed KPI set (Spend, Impressions, Clicks, CTR, CPA, ROAS) is, per the [Insights metric research](../research/insights-metrics-by-level.md), built from additive components (spend, impressions, `inline_link_clicks`, and the `actions`/`action_values` behind CPA/ROAS) that are safe to sum and re-derive at any tree level — unlike `reach`/`frequency`, which aren't part of this KPI set and are explicitly _not_ roll-up-safe. Rather than calling Meta's Insights endpoint separately at Ad Account, Campaign, Ad Set, and Ad level, Adomata fetches and stores Insights at Ad grain only — one row per (Ad, account-local date), keeping the raw `actions`/`action_values` arrays so CPA can resolve the Ad Set's canonical action type at read time instead of baking one in at ingestion. Every other tree level's numbers, and the Client rollup, are SQL sums over child Ad rows for the selected Time Range, re-deriving ratios; CPA is blank when spend-contributing descendants mix or cannot resolve result action types. This was chosen over fetching and storing a separate Insights row per tree level, which would roughly quadruple the Insights call volume against the same rate-limit ceiling scoped in the [rate-limit research](../research/2026-07-25-meta-api-rate-limits-fleet-refresh.md), for no correctness gain on these six specific KPIs. The trade-off to remember: Campaign/Ad Set/Ad Account rows carry no first-class Insights record of their own — a future KPI that isn't roll-up-safe (like reach) needs its own fetch at its own level, not an extension of this table.
