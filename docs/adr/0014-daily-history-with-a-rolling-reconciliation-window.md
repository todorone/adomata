# Insights history is stored as daily rollups with a rolling Reconciliation Window, not write-once

The Insights Tier stores one row per Ad per day ([ADR 0010](0010-insights-stored-at-ad-grain-only.md)), not just a latest-value snapshot — but a day's row isn't written once and left alone. The trailing [Reconciliation Window](../../CONTEXT.md#freshness) (sized to whatever attribution window [issue #14](https://github.com/todorone/adomata/issues/14) settles on) keeps being re-polled and overwritten on every Insights Tier cycle even though those days already look Final. This was decided while resolving [issue #12](https://github.com/todorone/adomata/issues/12): Meta's own docs state that a settled day's number can still move after the ordinary same-day revision period — an advertiser editing an ad set's attribution setting, or a platform-wide attribution change (see [insights-metrics-by-level.md §4](../research/insights-metrics-by-level.md#4-attribution-windows)) — so a pure write-once store risks silently drifting from what Meta would report if asked again. Fetching history on demand instead of storing it was considered and rejected: it reopens the exact problems [ADR 0013](0013-fleet-board-reads-synced-snapshots-not-meta-live.md) ruled out for the live path (latency under a click, unpredictable load on the same throttled Insights endpoint from multiple users requesting overlapping ranges). A day older than the window is stored as-is and never re-checked again — the residual risk of a rare, out-of-band revision reaching that far back is accepted for this scope, not engineered around.
