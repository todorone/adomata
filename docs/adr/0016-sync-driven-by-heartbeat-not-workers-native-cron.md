# Sync is driven by a `/heartbeat` endpoint, not Cloudflare Workers-native cron primitives

Superseded by [ADR 0032](0032-sync-runs-are-durable-and-invisible-when-healthy.md).

A single authenticated `/heartbeat` endpoint on the existing API checks each tier's last-refreshed timestamp and fires whichever of Account Tier / Insights Tier is due. In production it's called by a Cloudflare Cron Trigger on a schedule matching the fastest tier (5 minutes); it's also invoked in-process, as a non-blocking side effect, by the Fleet Board's own read endpoint — which doubles as the entire local-dev trigger mechanism (no dev-only scheduling code path) and a production backstop that keeps freshness correlated with someone actually looking at the board, matching [ADR 0008](0008-two-tier-freshness-for-fleet-board.md)'s finding that all three personas check in opportunistically rather than continuously. A per-tier lock prevents a cron-triggered and a read-triggered heartbeat from double-running the same tier.

This corrects a premise, not just answers a question: [ADR 0003](0003-bootstrap-infra-from-frontpeek.md) describes Adomata's stack as "Cloudflare Workers + Hono + Better Auth + Drizzle + D1/R2," which would have made Workers-native Cron Triggers, Queues, or Durable Objects the obvious sync mechanism — the framing [issue #12](https://github.com/todorone/adomata/issues/12) was written against. But `apps/api` was never actually deployed to Workers; per [docs/DEPLOYMENT.md](../DEPLOYMENT.md) it runs as a long-lived Bun process in Docker on a shared Hetzner VPS via Coolify, against Postgres (`drizzle-orm/bun-sql`), with no `wrangler.toml` for the API at all — only the client SPA is on Cloudflare. A host-level cron job was considered and rejected: DEPLOYMENT.md's whole deploy model is "everything lives in git, Coolify applies the compose file," and it separately warns that container names carry a fresh Coolify-assigned UUID on every deploy, so a cron job addressing a container by name would silently break on the next deploy. An external Cloudflare Cron Trigger calling an HTTP endpoint sidesteps that, and reuses Cloudflare infrastructure the project already has for the client, without requiring the API itself to run on Workers.
